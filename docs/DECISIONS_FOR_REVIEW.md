self.returns = close.pct_change(fill_method=None).shift(-1)

## §2 【Q1｜卡点】BUG-28：回测的成交时点，代码和文档互相矛盾

### 2.1 代码实际怎么做

`backtest/engine.py`：每月最后一个交易日（如 1/31）算出目标权重，然后

```python
if next_rdate is not None and date >= next_rdate:
    current_weights = target_weights.copy()
...
daily_ret_assets = returns.loc[date].reindex(current_weights.index, fill_value=0.0)
portfolio_return = (current_weights * daily_ret_assets).sum()
```

在 `date == rdate` 当天新权重就生效，开始赚 `returns.loc[rdate]`，即 **close(rdate) → close(rdate+1)**。

**翻译成人话**：在 rdate 收盘价算出信号 → **用同一个收盘价成交** → 赚下一个收盘的收益。
这是业界常见的 "trade at the close" 约定。

### 2.2 信号在 close(rdate) 时是否真的可知？（已逐条验证）

这是判断"是不是未来函数"的关键，我追过整条消费链，**结论是可知的**：

| 位置 | 代码 | 结论 |
|---|---|---|
| `alpha/combination.py:80` | `ic_hist = ic_s[ic_s.index < date]` | 严格 `<`，不含当期 IC |
| `alpha/combination.py:154` | 同上 | 严格 `<` |
| `alpha/regime.py:163`、`:241` | 同上 | 严格 `<` |
| `alpha/ml_signal.py` | 训练集行区间 `[train_start, i)` | 不含当期标签 |
| `factors/evaluation.py` | `period>1` 时 `rolling(period)...shift(-(period-1))` | 正确 |

**所以：信号在 close(rdate) 时完全可知，引擎没有偷看未来。**
它只是一个**成交价假设的乐观化**——假设你能在自己刚观测到的那个收盘价上成交。

另外我已经做了机械守护：`tests/test_factors/test_factor_causality.py` 对注册表里**每一个**
因子做"截断未来 / 替换未来，看过去是否改变"的检验，并把同样的检验套在 alpha 合成层上。
当前全绿（19/22 个因子可算，其余需要价格以外的输入）。

### 2.4 为什么这条在日频下不只是措辞问题

月频调仓天然规避 T+1（买卖间隔 ≥20 个交易日）。但 `rebalance_frequency: "daily"` 是合法配置。
日频 + 同收盘成交 = **当天买、当天卖（同一收盘价）**，这正是 A 股 T+1 禁止的行为，
而平台对外宣称"处理了 T+1"。

## §3 【Q2】BUG-26：股票池用"未来会不会变 ST"来筛股

### 3.1 事实

`data/pipeline.py` 的 `_filter_universe` 用 `metadata["is_st"]` 过滤，而 provider 对该字段的
定义是（`data/providers/synthetic.py:555` 注释原文）：

```python
# Determine if this stock ever becomes ST
if not self._metadata.loc[asset, "is_st"]:
    continue
```

触发日期随机落在样本内 `[60, len-60]`。**所以样本一开始就排除了那些"将来会变 ST"的股票**——
这是真实的未来函数。

provider 另有按公告日的 `_st_timeseries`，pipeline 也加载了（`_load_point_in_time_data`），
但**执行顺序在 `_filter_universe` 之后**，所以那个 PIT 分支从来没有被走到过。

### 3.2 我实测了它的影响（请注意，比直觉小）

```
未来会变 ST 的股票 : 6 只,  日均 -0.000251  (约 -6.3%/年)
从不 ST 的股票     : 294 只, 日均 +0.000489  (约 +12.3%/年)
差 = -18.65%/年,  t = -1.74
```

方向是"剔除它们会抬高回测"，但**只有 6 只、t = −1.74 不显著**。折算到整个股票池
（剔除 2% 的资产）大约是 **+0.4%/年** 这个量级。

### 3.3 为什么我没有直接修

我实现完又**回退了**，两个原因：

1. **现有测试把这个 bug 写成了规格**：`tests/test_data/test_pipeline.py::test_pipeline_excludes_st`
   断言 `assert not meta["is_st"].any()` —— 即"过滤后股票池里不能有任何 `is_st=True` 的股票"。
   我要修未来函数，就必然违反这条断言。**这条断言本身就是那个未来函数。**
2. **修了会让开关变成空转**：这份数据里第一天没有股票是 ST（`trigger_idx` 从第 60 天起），
   所以 PIT 过滤**一个人都不排除**，`exclude_st=True`（默认值）就变成了一个什么都不做的配置项
   —— 那本身又是另一类 bug（静默无效）。

### 3.4 可能的做法

- **A**：改成按日期的可交易掩码（pipeline 已经有 `is_limit_up`/`is_limit_down` 这个按日期
  标记的惯用法），下游回测消费它。语义最正确，但要穿到回测里。
- **B**：只改成"起始日 PIT"（排除第一天已是 ST 的），接受"中途变 ST 的不再剔除"，并改掉那条测试。
  改动小，但 `exclude_st` 在这份数据上等于空转。
- **C**：维持现状，但在报告/Registry 里把它标成机器可识别的 bias warning（项目有这套机制，
  `lab/registry` 存 `pit` / `bias_warning`，报告自动出 WARNING）。

## §4 【Q3】BUG-13：模拟经纪商的限价卖单，只能砸价才能成交

### 4.1 事实（实测）

| 委托 | 结果 |
|---|---|
| 限价**买** @ 参考价 10.00 | ✅ 成交 |
| 限价**卖** @ 10.00 | ❌ 被拒，`No liquidity available` |
| 限价**卖** @ 10.01 | ❌ 被拒 |
| 限价**卖** @ 9.95 | ✅ 成交 |

盘口实际是 `best_bid = 9.99`、`best_ask = 10.00`。

根因在 `trading/broker.py` 的 `_seed_book`：卖价档位是 `price * (1 + 1bp * i)`（i=0 时**正好
等于**参考价），买价档位是 `price * (1 - 1bp * (i + 1))`（i=0 时**低一档**）。这个 `+1` 不对称
是有原因的：¥10 × 1bp = ¥0.001，**在 0.01 的最小变动价位上会被舍掉**，所以作者用它把买价
推开一档避免和卖价重合。

后果：**纸面交易里想卖出就必须低于市价挂单**，每一次卖出都被系统性地报在更差的价格上。

### 4.2 我试过的修法，以及为什么它是错的

把买价也改成 `1 - 1bp * i`（两边都在参考价）——**不行**：`OrderBook.add_order` 对**市商挂单
也走撮合**，买价挂在卖价的价位上会**自成交**，把整个盘口吃空，之后**买和卖都成交不了**。
我实测到这一点后回退了。

**所以这里不是笔误，是一个需要设计选择的问题**：要么给 OrderBook 加一个"被动挂单"的接口
（市商挂单不参与撮合），要么让未成交的限价单**挂单等待**而不是直接拒单。两条路都改变撮合语义。
